# Factory

Coordinate the pipeline. Use `diagnose-issue` for the diagnosis, `prepare-spec` for the spec, `implement-spec` for the build, `summarize-changes` for its facts, a reviewer for findings, and `fix-issues` for triage and fixes. Load companion skills from the harness or their canonical `skills/<name>/SKILL.md` in the same skills release. If a required skill or capability is unavailable, report the blocked stage and how to resume.

## Model policy

This applies to every subagent and harness reviewer Factory or its stage skills launch. Pick from three tiers, at the latest version the harness offers: **light** (Haiku level: Claude `haiku`, GPT `luna`), **standard** (Sonnet level: Claude `sonnet`, GPT `terra`), and **strong** (Opus level: Claude `opus`, GPT `sol`). Use light only for narrow, mechanical tasks whose output is easy to check, especially many small ones in parallel: locating files or call sites, collecting or summarizing data, describing a mechanical block of a diff, or a trivial edit with an exact pattern to copy. Never use light for specs, builds beyond trivial edits, reviews, judging findings, or security-sensitive work. Default to standard. Use low, medium, or high effort only; never `xhigh` or `max`. When a tier at high effort is not enough, move up a tier (`sonnet` → `opus`) instead of raising the effort. Strong at high effort is the ceiling. Use frontier models (Claude `fable`, GPT `astra`) or `xhigh` and higher effort only when the user explicitly asks for them in this run. Set the model and effort explicitly on each launch rather than inheriting the session's, because the session may run on a frontier model. If the harness cannot set them, use the closest option within the policy and record the difference in the stage's entry. A harness reviewer that takes an effort level (such as `code-review`) runs at `high` or lower.

Standalone `fix-issues` may use the light tier for a nit with mechanical verification and repair, such as a typo or a stale comment. In Factory the same agent handles the entire non-hard batch.

An override the user approved and recorded in a saved spec counts as an explicit request for the run that builds that spec, so a build from that spec does not cap it.

## Execution mode

- **Orchestrator** is the Factory root. It selects the path, handles the model check, approvals, `prepare-spec`, and `diagnose-issue`, and owns the checkpoint, usage reports, all GitHub posts, the PR description's Diagnostics, Ready and the notification.
- **Owner** is a subagent responsible for one stage procedure. Factory uses a build owner, a review owner for each round, and a handoff owner. An owner may launch workers. It asks the user nothing, holds no approvals, and makes no PR comments, reviews or thread replies. The build owner's `implement-spec` delivery may open a draft PR and push the build. A review owner may push verified fixes. Only the orchestrator edits the PR description or marks it ready.
- **Worker** is a subagent responsible for one task, such as building, reviewing or fixing. Every worker brief says to launch no agents.

**Nested** runs orchestrator → owner → worker. **Flat** runs every stage procedure in the orchestrator, which launches only workers. **Inline** does all work in the orchestrator with no subagents. In inline mode, when Factory built or fixed the reviewed code, each round review states that the reviewer was not independent of Factory's build or fixes.

Start with `execution_mode: "unknown"`. If there is no subagent launch tool, record `inline`. Otherwise try the build owner. Before committing, pushing or opening a PR, the build owner must launch the builder. If there is no launch tool in the owner or launch fails because of the nesting limit, it undoes only its own branch setup, preserves pre-existing work, and returns exactly `NO_NESTING: <what happened>`. For explicit existing-PR review, which has no build, the first review owner probes in the same way by launching its first reviewer before fixes, pushes or publication.

A successful probe sets `nested`. Only `NO_NESTING` switches a run from the owner path to `flat`. Record the mode and `execution_mode_reason` in the checkpoint and in the Build stage's `--work` (for example, `nested (build owner sonnet/medium)` or `flat: build owner could not launch the builder`). Use the first Review Round's `--work` when there is no Build. On `NO_NESTING`, the orchestrator runs the rest of that stage itself in flat mode, using the same inputs and the already open stage window. A later owner that cannot launch a required worker uses the same sentinel, including after resume. Before taking over, check the owner's checkout and the last recorded result, preserving any completed fixes and restarting only work whose result has not been verified. A crash or other blocker follows the stage's failure procedure and leaves the mode as it was. Owners never substitute themselves for required workers. A saved flat or inline mode survives resume and never probes again. A new run starts with fresh detection.

**Orchestrator model check.** Before the first stage, identify the active model and its tier. In Claude Code cloud, read `session_context.model` from `get_session` if available. In other harnesses, including Codex, use the model reported by the harness. Record it in `root_model`; Diagnostics shows it on the Orchestrator row. If unknown, record `orchestrator model unknown`. When setting flat or inline mode and the known model is outside the standard tier, ask once whether to switch or continue. The Claude Code command is `/model sonnet`. In Codex, use `/model` and choose `terra`. Ask before the first stage for inline and immediately after the build or review owner returns `NO_NESTING` for flat. Record the prompt in `model_check_asked` before asking. Skip the prompt in nested mode, on resume, for an unknown model, or if the user named the orchestrator's model or asked to skip the check. The user controls any switch. Record the model that runs when work resumes.

### Owner briefs

Launch each owner on the standard tier at medium effort, explicitly setting model and effort (Claude `sonnet`, GPT `terra`). Use the closest available choice within the model policy if the harness cannot set both, and record the difference in the stage outcome. Pass paths, SHAs, refs, URLs, authorized operations, and the checkpoint path. For the [launch log](#stage-bookkeeping-and-publication), also pass the owner's own agent ID and label, the checkpoint's `run_id`, and a fresh agent-log scratch path for the stage; the owner logs every worker there with `--run RUN_ID --parent OWNER_ID` and returns the path. Supply the pinned spec, approval and review guidance as scratch files: pass the pinned `full-spec.md` and `document.md` paths, the `record.json` path and its hashes, never pasted spec text. Owners load the relevant stage skills from the harness or the same release. They read needed checkpoint keys and return compact outcomes, SHAs, file paths, verdicts and blockers. They save bodies and payloads in scratch files.

- **Build owner** runs [Run Build](#run-build). It attempts the sized builder launch with the `implement-spec` pipeline inputs and handles `NO_NESTING` as above. It returns any `implement-spec` stop payload unchanged. Save the verified build delivery to scratch. Return the PR URL and refs, checkout, starting head, build commit SHAs, difficulty, builder model and effort that ran, deviations, checks, and reproduction results when applicable.
- **Review owner** runs the single [round procedure](#35-run-a-review-round) through the push and review preparation. Return the reviewed comparison, range decision, reviewer(s) and guidance used, verdict table with full SHAs, pushed head, review payload path, replies JSON path, open questions, follow-ups, deferred items and blockers. Use the supplied [fix recovery](#fix-recovery) path. If a comparison refresh requires diagnosis or approval, return the snapshots and evidence for the orchestrator to handle.
- **Handoff owner** prepares the [Final handoff](#6-post-the-final-handoff), including facts, final diagnosis verification where applicable, the spec-store recheck, and the Adjust replacement section. Return the body and replacement file paths as applicable, final comparison, and verification results.

In flat or inline mode the orchestrator does the owner's work directly. For large changes, every facts block worker gets the no-agent-launch instruction. In inline mode use the facts stage's direct block procedure.

## Keep the orchestrator's context small

Each orchestrator call rereads its context. Use `git diff --stat` and `--name-status` plus targeted hunks. Save a whole patch to scratch or let an owner or worker read it without printing it in the orchestrator. In flat and inline mode gather context for the same procedures in bounded reads. Read only the relevant parts of companion skills and guidance. Pass paths, SHAs and refs instead of pasting file contents, request compact results, and batch independent tool calls.

Resolve bare numbers in the target repository when unambiguous. If the user separately and explicitly requests the review and fix pipeline on an existing PR, use [Existing PR review](#existing-pr-review) and its approval gate.
- A `SPEC.md` path selects [Saved spec](#saved-spec). For a GitHub issue, read only its title and the first line of its body, for example `gh issue view N --repo OWNER/REPO --json title,body --jq '.title, (.body | split("\n")[0])'`. Without `gh`, launch a light-tier worker at medium effort that launches no agents to fetch the issue, write its body byte for byte to a scratch path, and return only the title, whether the first line starts `<!-- spec-record`, and the path. A `Spec:` title plus a top `spec-record` selects Saved spec. Read the body of any other issue only for the bug path. A `Spec:` title without that record selects [Prepare the spec](#prepare-the-spec) with the issue as its store. Every other issue selects the existing [bug-issue path](#issue-path-without-a-pr).
- A rough idea or supplied spec text selects [Prepare the spec](#prepare-the-spec).

## Existing PR diagnosis

1. Open Diagnosis, then resolve the PR and record its URL, base and head repositories, refs, and exact commit SHAs. Give `diagnose-issue` the PR, any issue the user specified, and both SHAs. Use the PR's recorded base SHA as the baseline. Have it use the linked issue as the bug report, or the PR description if the linked-issue lookup establishes there is none. This path uses the PR as the entry point even when the report comes from a linked issue.
2. Run `diagnose-issue` in Factory mode using its existing-PR diagnosis instructions for the supported setup and comparison with the PR changes. Close Diagnosis and return the source report, baseline verdict, comparison result and tested revisions, setup and support evidence, what the patch changes, and proposed next step in chat. Stop after the diagnosis. Keep the checkpoint in scratch space and leave the PR and issue untouched, including when resuming.

## Build and review pipeline

Factory build and explicit PR review requests authorize publishing a draft PR when building, pushing verified fixes as allowed by the selected path, posting pipeline comments and reviews, and marking the PR ready for review. Once the scope is approved under the selected path, proceed without routine user input. Keep draft PRs in draft through the internal review rounds and final handoff. Preserve an existing ready PR's status on explicit PR review. Adjust converts a ready PR to draft for the build and internal review.

## Stage bookkeeping and publication

Run the local helper with `node SKILL_DIR/scripts/factory.mjs`, where `SKILL_DIR` is this skill's directory. It works on scratch files and local git objects. The orchestrator supplies GitHub state and handles publication with authenticated `gh` or the equivalent GitHub MCP tool.

- **Checkpoint.** Create one scratch JSON file and keep its path in task state. Use `scripts/factory.mjs checkpoint get --file F KEY`, `checkpoint set --file F KEY VALUE_JSON`, and `checkpoint append --file F KEY VALUE_JSON` with dotted keys. Read just the keys the step needs. Owners read but never write the checkpoint.
- **Session source.** Record `run` with `harness` (`claude` or `codex`), live `session_id`, original launch directory `cwd`, a configured `prices` path when available, and any explicit `transcripts` paths. In Codex use the active `CODEX_THREAD_ID` when set and report where its rollout is readable. Supply a host export with the main rollout first, then all contributing subagent rollouts, or point `CODEX_HOME` to a readable copy of the host Codex directory. Use the active Claude Code session ID in Claude Code. If the transcript or session cannot be verified, retain the reason and record unavailable Diagnostics. Include the source and date of externally supplied prices when available.
- **Windows.** At the start of each stage, including Spec or Diagnosis, Build, each Review Round, Final handoff and Ready, run `scripts/factory.mjs stage open --file F --stage NAME`. Use a distinct name for each repeated stage, such as `Review Round 1`. Open before launching its owner or starting the procedure. When the owner returns or the orchestrator finishes the procedure, run `scripts/factory.mjs stage close --file F --stage NAME`. It ends the contiguous window, calls `usage-report.mjs` (including transitive subagents), saves the usage JSON, and writes the Diagnostics block. It returns the block path and stores it with models, tokens and cost in `stages.NAME`.. Keep ISO 8601 UTC in the checkpoint and publish times as `Nov 21 12:00 UTC` or `Nov 21 12:00–12:45 UTC`; repeat the date when it changes.
- **Launch log.** Before every subagent launch, the launching agent runs `scripts/factory.mjs agent add --file F --stage NAME --id ID --role TEXT --model MODEL --effort EFFORT [--parent ID]` (the orchestrator on the checkpoint; an owner on the agent-log scratch path from its brief, with `--run` and `--parent` from its brief). Use a run-unique ID and the launching agent's ID as `--parent` (omit it for the orchestrator). Start the launch description and the first line of the prompt with the returned `label` (`factory:<run>:<id>`). After it returns, run `agent done --file F --id ID --work TEXT [--stopped]`, where the work comes from the returned records: finding IDs with verdicts and fix commits for fixers, the finding count and IDs for reviewers (for example `F1 VALID 4ab12cd` and `3 findings (F1-F3)`), `build <short SHA>` for the builder, the procedure for an owner, or the stop reason. A relaunch is a new entry. When an owner returns, run `agent merge --file F --from AGENT_LOG` with the returned path before closing the stage. In flat or inline mode the orchestrator logs its workers on the checkpoint directly. Close each stage with `stage close … --work TEXT`, a few words on what the orchestrator itself did in the stage (for example `preflight, publish review`), which fills the Orchestrator row. Tests: `node SKILL_DIR/scripts/diagnostics.test.mjs`.
- **Diagnostics.** The block lists the stage's agents in launch order with their parent, the model that ran (and the requested one when it differs), the requested effort, their work, tokens and cost, matched to transcripts by label, plus an Unattributed row and the window total; tokens or costs that cannot be measured, such as Codex models without prices, are `N/A`, but the tree, models and work are still shown. Append the block to the stage's prepared body or the review payload's `body` before posting. Preserve the raw JSON and warnings for recovery. When rebuilding a block from saved reports, use `scripts/factory.mjs diagnostics --stage NAME --usage FILE [--usage FILE]... --agents CHECKPOINT --mode MODE [--work TEXT] --out FILE`. Show measured tokens when a rate is missing and mark cost `N/A`. If usage is incomplete or unavailable, show the script's reason and never estimate. Posting counts toward the next window. Spec, Diagnosis and Build blocks go into the PR description's Diagnostics, not a comment. Final handoff covers work up to its posting preparation. The measured Ready tail is for chat only.
- **Publish.** Use the prepared output file in one `gh` call or the equivalent MCP call. Verify the resulting URL, then checkpoint the link. The same publication steps apply in all modes.
- **PR description Diagnostics.** The description ends with one collapsed Diagnostics block for the stages without their own comment or review: Spec or Diagnosis (including reopened ones) and each Build attempt. Each stage keeps its own agent table, and a `Run so far` line totals every closed stage except Ready. Record each stage's outcome in its `stage close --work` (for example, `approved by user in chat at Nov 21 12:00 UTC` or `stopped: material_deviation`). Fetch the current description to a file, run `scripts/factory.mjs pr-diagnostics --body FILE --file CHECKPOINT --stage NAME [--stage NAME]... --out FILE` with those stages in order, update the description, and re-read it to verify. It rewrites only the marked block, and replaces a legacy Evidence trail panel in its place. Write it in [step 2](#2-complete-the-pr-description) and again after Final handoff posts, to refresh the run total.
- **Comparison.** Read the base ref and both commit SHAs from one PR snapshot, fetch missing local objects, and run `scripts/factory.mjs compare snapshot --head SHA --base-ref REF --base-sha SHA`. Store its head, base ref and merge base. A base advance that leaves the merge base unchanged preserves the comparison. Use `scripts/factory.mjs compare same --a JSON --b JSON` for every comparison check, including before fixes, push, handoff and Ready. The JSON arguments are the saved and current snapshots.

## 1. Establish the target and approved scope

Use the build or review path selected above. Resolve GitHub targets by URL or repository-qualified number. Use repository context for unambiguous bare numbers.

Open Spec for saved specs, ideas and supplied text, or Diagnosis for issues and explicit PR review, before doing that stage's work. Use [Stage bookkeeping and publication](#stage-bookkeeping-and-publication) for the stage window and each PR comparison.

### Prepare the spec

For an idea or supplied spec, run `prepare-spec` in pipeline mode. It grounds the spec, resolves material gaps, obtains explicit summary approval, and saves to the chosen store. Give it the original issue as the destination for a recordless `Spec:` issue. Continue with its verified return at Pin and find the PR. Factory itself never writes to a spec issue or `SPEC.md`.

### Saved spec

Pass the store location, any raw-body scratch path, and current build base to `prepare-spec` for saved-spec validation. It fetches the body with the shell and runs `pin`. It checks the approval record and hash, asks about a nonempty mismatched local branch, and compares the files in scope with the recorded base. Reuse an approved unchanged spec without questions. For base drift, revalidate against current code and ask only about material gaps. Edited text requires approval as the next revision. A missing record needs supplied-spec approval. Use the verified revision returned by that skill.

### Pin and find the PR

Use the pinned directory `prepare-spec` returns (`document.md`, `summary.md`, `full-spec.md`, `record.json`) without reading its text. Checkpoint the paths, store location, revision N, `spec_sha256`, and the build estimate from `meta`. If `pin` escalated, save the approved document and approval record to scratch files as text instead, and record `pin_escalated: <reason>` in the checkpoint and the Spec stage's `--work`. Load `summary.md` only when presenting something to the user. Use these pinned files in every subsequent stage, including on resume. Read the store again only at handoff. Spec text moves between agents only by path. To switch revisions earlier the user stops this run and starts a new one.

- **Spec issue:** inspect `gh issue view N --json closedByPullRequestsReferences` or equivalent. Check the state and body of linked PRs. If the repository can target non-default bases or the closing-reference lookup is unavailable, search the repository's open PR descriptions for a standalone `Closes #N`. Non-default bases may lack closing references even when a default-branch PR is linked. Combine both sources and deduplicate by PR URL before counting open matches. Check the actual issue number and repository to avoid substring or cross-repo matches. Include closed and merged references or body matches when no open PR exists. If the installed `gh issue view` lacks the field, use the paginated GraphQL connection:

  ```sh
  gh api graphql --paginate -f owner="$owner" -f repo="$repo" -F number="$number" -f query='
    query($owner: String!, $repo: String!, $number: Int!, $endCursor: String) {
      repository(owner: $owner, name: $repo) {
        issue(number: $number) {
          closedByPullRequestsReferences(first: 100, after: $endCursor, includeClosedPrs: true) {
            nodes { number url state }
            pageInfo { hasNextPage endCursor }
          }
        }
      }
    }'
  ```

  Verify every candidate by fetching its PR. When a connector exposes only PR search, search descriptions across all states for the exact closing line. A failed or incomplete lookup does not establish that no PR exists.
- **Local file:** list all PR states for the current branch with `gh pr list --head <current-branch> --state all` or equivalent. Match the head repository as well. Use the checkpointed feature branch on resume.

Write each candidate PR description to a scratch file with the shell (`gh pr view N --json body --jq .body > FILE`), without printing it, and run `node PREPARE_SPEC_DIR/scripts/spec-record.mjs built FILE`, where `PREPARE_SPEC_DIR` is the directory of the loaded `prepare-spec` skill (not this skill's `SKILL_DIR`). Compare its `revision` and `spec_sha256` with the pinned record: the same hash is the pinned revision with matching text, a lower revision is an older revision, and the same revision with a different hash is different text. On `legacy_section`, the PR predates `spec-built`: extract its `Spec rev N` section and document body to scratch (excluding the closing line and evidence trail) and compare the `spec_sha256` from `spec-record.mjs check FILE`. Any other escalation counts as a missing or unreadable spec.

| Matching PRs | Next step |
| --- | --- |
| No PR | Build. |
| Several open PRs | Ask which PR to use, then evaluate that PR. |
| One open PR built from an older revision | Adjust. |
| One open PR with the pinned revision and matching text | Report the PR and revision, and stop. |
| Closed or merged PRs only | Ask whether to start a new PR or stop. For a merged spec issue, usually start a new spec issue linking the old one. |
| Open PR with missing/unreadable spec, a newer revision, or different text at the same revision | Show the discrepancy and ask which spec or PR to use before publishing. |

### Build

For `SPEC.md`, use its current feature branch. If on the default branch, specify a new feature branch in this working tree, preserving the untracked file, and record the branch in the checkpoint only. For an issue spec, publish from a feature branch against the target base. Close the Spec stage after validation and continue at [Run Build](#run-build). The draft PR description summarizes the implementation and carries the `spec-built` block, plus a standalone `Closes #N` for a spec issue; it does not repeat an issue spec (see `implement-spec`).

### Adjust

1. Record the selected open PR's head repository and branch, starting head SHA, base ref, and effective merge base. Check write access to its head and apply the existing PR push rule for another owner's fork. Find the exact built document: for an issue spec, the issue comment whose first line is `Revision <built revision> — superseded…`, with the body inside its `<details>` extracted to scratch by the shell; for a local spec, the collapsed document in the PR description; for a legacy PR, its `Spec rev N` section. Run `spec-record.mjs check` on it and require the `spec_sha256` from `spec-built`. The build owner diffs it against the pinned `document.md` to identify exactly what changed. If the built document cannot be found or does not match, give the builder the pinned full spec and the PR's code with the instruction to implement what the code does not yet satisfy, and record `adjust without spec diff: <reason>` in the Build outcome. Preserve all existing evidence rows. Number Build and Review Round entries after their previous highest numbers (count an initial unnumbered Build as 1). Add `Spec rev N` and the next `Build K`. Count the two review rounds within this run separately from their continuing published round numbers.
2. Close the Spec stage as for Build. Move a ready PR to draft (`gh pr ready NUMBER --undo` or equivalent) and verify its status. For an issue spec, verify and restore the standalone `Closes #N` line if missing. Preserve unrelated description content and the prior `spec-built` block (or legacy spec section) until handoff.
3. Continue at [Run Build](#run-build) with the existing PR, exact starting head and the spec difference. Build only that difference on the PR head branch. Verify the returned commits are on the selected PR. If no code changed, record the checks showing the existing head satisfies the revision and give the reviewer the empty range plus that evidence. Continue through steps 2–7 with that PR. Review the new commits with the full PR as context. Update its `spec-built` block (and a local spec's collapsed document) to the pinned revision at final handoff after the fix loop.

For a saved-spec Build or Adjust that stops with `not_approved`, `material_deviation`, or `reproduction_mismatch`, checkpoint the stopped build and report the reason and evidence. For a reproduction mismatch, recheck the command on the reported clean base and report the observed result. End this pinned run before changing scope. Route any necessary revision to `prepare-spec` and start a new run after approval. See [Reopened approval](#reopened-approval) for diagnosis retries.

### Issue path without a PR

1. Resolve the supplied GitHub issue and run `diagnose-issue`. At the verdict, close Diagnosis and keep its Diagnostics for the PR description. Present the verdict, evidence, and proposed next step and wait for the user's explicit diagnosis approval. For `CONFIRMED`, offer the full fix plan with the summary for approval together. For any other verdict, stop at the approved diagnosis. Keep any drafted issue reply in chat unless the user explicitly approves posting it. Factory's PR authorization applies only to the PR.
2. For an approved `CONFIRMED` diagnosis, continue at [Run Build](#run-build) with the approved full plan and summary as the approved spec, with the approval record, issue URL, baseline, and reproduction. `implement-spec` sizes the build when the plan has no estimate, and its builder confirms that the reproduction fails for the diagnosed reason before changing the implementation and passes with the fix. Build from the diagnosed base. If the base has moved and the diagnosis materially changes, return to diagnosis approval before building. If `implement-spec` stops, return to step 1 with the returned evidence. For `reproduction_mismatch`, rerun `diagnose-issue`. For `material_deviation` or `not_approved`, fold the proposed change or gap resolution into the full plan and summary, rerunning `diagnose-issue` if the evidence questions the root cause. Present the changed parts for fresh diagnosis approval before rerunning this step. See [Reopened approval](#reopened-approval). Have it link the issue in the PR body without a closing keyword such as `Fixes`, so merging does not close it automatically.
3. When `implement-spec` returns the draft PR and build commit, continue at [2. Complete the PR description](#2-complete-the-pr-description).

### Reopened approval

For a diagnosed fix plan, when `implement-spec` stops, close that Build's window at the stop and checkpoint its outcome. A reopened Diagnosis stage starts at the stopped Build's end and is its own stage (`Diagnosis 2`) with the stop reason and the new approval in its `--work`. The stopped attempt is a Build stage whose `--work` gives the stop reason, and the rerun is the next Build stage (`Build 2`). Windows stay contiguous. Reopen at most once per stage. If the rerun stops again, report the reason and evidence to the user and stop.

### Run Build

Open the Build window and run the build owner if mode is unknown or nested. In flat or inline, run it in the orchestrator. In all cases use `implement-spec` pipeline mode with the pinned full spec and summary, revision and store when applicable, approval record, difficulty, builder model and effort and override, repository, and target branch. For Adjust include the existing PR, exact starting head and spec difference. For a diagnosed fix include the report link, baseline and reproduction. Tell the builder to launch no agents. In inline mode use the skill's direct-build fallback and record the actual model and effort. In the build owner, intercept a missing worker tool or depth error before the skill could take that fallback. Follow [Execution mode](#execution-mode) for `NO_NESTING`.

On a stop, close the window, save the unchanged stop payload and return to the originating approval path above. A stop before the first worker launch leaves an unknown mode unknown. For a successful build, close Build when the owner returns or the orchestrator finishes its work, Use the returned checkout and PR refs, verify the draft and build result, and collect all new Spec or Diagnosis and Build rows, including stopped and reopened attempts. Preserve prior runs. Label repeated summaries and handoffs with their revision on Adjust. Then continue at [2. Complete the PR description](#2-complete-the-pr-description).

### Existing PR review

1. Resolve the PR and record its status, comparison, head repository, and branch. Factory may push fixes when the head repository is the base repository or one the user owns. Any other head, such as a contributor's fork, needs the user's explicit approval to push at step 2 and GitHub write access to that branch.
2. Run `diagnose-issue` with the PR, any supplied issue, and the comparison's head SHA and merge base. Use an explicitly supplied baseline when given. For PR-only input, use the skill's automatic discovery of the linked issue. Present the source report, diagnosis, verification verdict, tested commits, and proposed next step. For a closed or merged PR, return this evidence in chat and stop. For an open PR, ask for explicit approval of the diagnosed scope and review plan if `VERIFIED`, or of the remaining fix plan if `NOT_FIXED`. For `INCONCLUSIVE`, report the missing evidence and stop before writing to the PR. State where fix commits would be pushed. Keep any issue reply in chat pending separate approval to post.
3. After approval, confirm the PR is open and use `compare same` to check that its comparison matches the evidence. If the comparison changed, rerun verification using the same report and reproduction. Use the new merge base for a default baseline and keep an explicitly supplied baseline. Stop if the result is inconclusive and seek approval again if the diagnosis or planned work materially changes. Apply the same refresh and approval rules to unexpected comparison changes before review or handoff. Use the approved behavior and acceptance checks as the spec for review. Record the approved report, baseline, reproduction, tested comparison, verdict, and any remaining fix gap in the checkpoint.
4. Close Diagnosis with the verification result and approval in its `--work`. Continue at [2. Complete the PR description](#2-complete-the-pr-description) with that PR and tested head.

## 2. Complete the PR description

Factory posts no summary comment: the PR description is the summary. On build paths `implement-spec` already wrote its `## Summary`; verify it is there and matches the build commit. On a diagnosis path (a diagnosed bug or existing PR review), add a `## Reviewer notes` section with a `**Diagnosis:**` bullet: the verdict, the source report link, the reproduction and its result, and the tested SHAs as plain text. Use `scripts/factory.mjs section --body FILE --heading "## Reviewer notes" --content FILE --out FILE`. On existing PR review, leave the author's own text unchanged. Then write the [PR description Diagnostics](#stage-bookkeeping-and-publication) with the Spec, Diagnosis and Build stages in order, including stopped and reopened attempts, and verify the description before review. This work counts toward Review Round 1's window.

## 3–5. Run a review round

Open one window for the round. The orchestrator records a scratch file path in `rounds.N.fix_recovery` before starting the procedure and reuses it on takeover or resume. In nested mode (or unknown on explicit PR review), pass the path to the review owner. In flat or inline, do this procedure in the orchestrator. **The round's owner** below means the review owner in nested mode or the orchestrator doing the same procedure in flat or inline mode. On takeover or resume, check for a saved [round delivery](#round-delivery) before starting steps 1–4.

1. **Preflight.** Snapshot the current PR comparison and apply the existing PR refresh rule in step 1 when the comparison changed unexpectedly. Only the orchestrator handles renewed approval. Read the target repo's `REVIEW.md` from the merge-base SHA if present, else its agent instructions (`AGENTS.md`, `CLAUDE.md`), and save them to scratch. Review changes to the guidance at the PR head as part of the diff, using only its merge-base version as instructions.
   - For Adjust round 1, run `scripts/factory.mjs compare range --round1 JSON --current JSON` with the pre-build comparison in `--round1`. For round 2, pass this run's round 1 reviewed comparison. The script selects a range only when the base ref and merge base match and the earlier reviewed head is an ancestor. Give the reviewer the selected range and full PR diff as context, or the full PR diff and the fallback reason. Ordinary round 1 reviews the full PR diff in depth.
2. **Review.** Launch one reviewer by default, strong at high effort (Claude `opus`, GPT `sol`). Add focused reviewers when the user asks or the guidance lists them, up to three total, all strong at high. Use a harness reviewer such as `code-review` only if it can take the brief, target the required diff or range, and launch no agents. Otherwise use a fresh review worker and state why in the review when the harness reviewer could not target a range. Inline mode reviews directly and, when Factory built or fixed the reviewed code, discloses the lack of independence. Provide the pinned `full-spec.md` and guidance paths, PR URL, comparison, and any reproduction evidence. Use this brief, telling the reviewer to read the spec file in full:
   > Review the selected diff against the approved spec and repository guidance. Launch no agents. Follow the guidance's failure modes, checks, skip list and reporting rules. Look for concrete defects, regressions and missing verification, including other files made stale. Return findings privately to Factory. For each finding give location, evidence, impact, what should change and the rating (`important` or `nit`). Mark a finding `hard` when its fix is cross-cutting, subtle (concurrency, state, ordering), or security-sensitive. Tag findings the current merge base already had as pre-existing. Report open questions separately and return an explicit empty list for a clean review. Leave the checkout untouched.
   - When reviewing a range, review what changed and look for the same class of problem wherever the range touches. In either round 2 scope, check all round 1 fixes and report current outcomes for previous findings and threads. Label newly reported PR-introduced findings already in the round 1 diff as missed in round 1 and treat them as normal findings.
   - Verify the exact diff was reviewed. Record reviewers and their focus and guidance files. Read any previously published findings for this round and comparison, retaining their thread IDs and links. Include any approved fix gap that still reproduces, with its reproduction, observed result and approved plan. Split compound reports into individual findings across the whole list, then merge duplicates. Preserve each finding's applicable location, rating, evidence, source and pre-existing status. When reviewers disagree about difficulty for the same finding, `hard` wins. Collect reviewers' open questions separately from findings, including on a clean round, and keep them with the round results.
3. **Fix preflight.** Resolve the actual PR head repository and branch, then take a fresh snapshot and use `compare same` against the reviewed comparison. For a new attempt with nonempty findings, prepare and verify a clean checkout on the PR head branch at the exact reviewed SHA, preserving earlier edits and local commits. For an interrupted attempt, validate the original comparison and checkout using [fix recovery](#fix-recovery). If the comparison changed now or before the push, discard stale findings and rerun this round's procedure on the new comparison at most once. Preserve any unpublished local commits and the old recovery record separately before starting a fresh record for the retry. If it changes again or the checkout cannot be prepared safely, record the findings and blocker and stop.
4. **Fix.** For a clean review, skip both fixer paths and verify the empty verdict list with `scripts/factory.mjs verify-commits --from REVIEWED_HEAD --to REVIEWED_HEAD --rows FILE`. Proceed to step 5 without a push. Otherwise, assign final round IDs (`#1`, `#2`, ...) to the individual, deduplicated findings before dividing them into a batch (all non-hard findings plus all pre-existing ones) and a hard set (hard and not pre-existing). Keep those IDs through triage and join verdicts and thread replies by the original ID.
   - Run `fix-issues` with `auto`, `inline` and `preserve IDs` in its pasted-list workflow, the fix recovery file and helper paths, the explicit batch even when empty, each original finding ID, rating and pre-existing tag, and round 1 or 2 within this run. The review owner runs the batch itself in nested mode. In flat mode launch one standard-tier worker at high effort for the batch, telling it to launch no agents, use the recovery procedure for every finding, and return only the verdict table with full commit SHAs, CHANGES files, counts and checks, or a blocker if it cannot finish. In inline mode run the batch in the orchestrator. Keep the existing defer and follow-up rules.
   - After the batch, work through the hard set in `fix-issues` triage order. In nested or flat mode launch one `verify-and-fix` worker per hard finding, strong at high effort, one at a time. In inline mode follow `verify-and-fix` directly. Say that earlier fixes are committed. The round's owner follows `fix-issues` step 5 after each result, including verifying the clean tree and committing each warranted fix separately.
   - Give each fixer (and every batch run) the original PR comparison, including merge-base SHA and reviewed head. Before fixing a finding, run `git diff --stat MERGE_BASE REVIEWED_HEAD` and read the full PR diff for every file the fix touches, fetching new file diffs before edits when scope expands.
   - Save verdicts in triage order with full commit SHAs, reported CHANGES files, and checks. Write `[{id, verdict, commit, files}]` to scratch, with `commit: null` for verdicts without one. Run `scripts/factory.mjs verify-commits --from REVIEWED_HEAD --to HEAD --rows FILE`. Reconcile missing and unreported commits before proceeding. If verification finds out-of-scope changes, follow [Corrective commits](#corrective-commits). Account for every commit and verify the resulting net diff before pushing. Stop with the evidence if verification cannot account for every change. Record individual failed, deferred and follow-up findings for handoff.
5. **Push and prepare the review.** Follow [round delivery](#round-delivery) to save the verified result before a push, recognize an already completed push on resume, or record a local-only or clean outcome. A push failure or incomplete fix procedure blocks publication until resolved.
   - Write the round review in the [review round layout](#review-round-layout) with the published round number (use the continuing number on Adjust). Cite a fix as published only after verifying the push.
   - For existing threads, save each reply as `{thread_id, body}` or `{comment_id, body}` in a JSON array. If there is no usable thread, link to the finding and put the outcome in the review body. For new findings, write the inline candidates as `[{path, line, body}]`, give the helper the full PR diff at the reviewed head, and run `scripts/factory.mjs review --commit REVIEWED_HEAD --body FILE --comments FILE --diff FILE --out FILE`. The resulting `COMMENT` payload sets `commit_id` and moves unanchorable findings to the body. Use body findings directly when a tool cannot target the reviewed diff.
   - The orchestrator records the verified push disposition, published comparison, original review results and payload paths in the run checkpoint, including `rounds.N.open_questions`. Close the Review Round window after the files are ready, then append the Review Round Diagnostics to a copy of the saved payload's `body` and post one GitHub review with `gh api repos/OWNER/REPO/pulls/N/reviews --input FILE` or the MCP equivalent. If GitHub rejects specific anchors, move those findings to the body and retry only after checking the review did not post. Post the saved replies without Diagnostics and verify links. On resume, reuse the closed stage's Diagnostics, look up existing publication for this round and original reviewed comparison, and post only a missing review or reply. Record verified links in the checkpoint before advancing.
   - If round 1 pushed fixes, repeat this procedure once at the updated head, with a fresh review owner when nested. Otherwise proceed to Final handoff. Keep both rounds' outcomes and work left for human review.

### Review round layout

```markdown
## Review Round 1

- Reviewed: [6c374b3...3283f53](https://github.com/OWNER/REPO/compare/<merge-base>...<reviewed-head>) (full diff)
- Reviewer: claude-opus-5-5/high
- Guidance: REVIEW.md
- Fixes: published through 310c31eb22d4a753915ad3661bd5c25eb8956364

| # | Finding | Severity | Difficulty | Verdict | Commit |
| --- | --- | --- | --- | --- | --- |
| F1 | [Helper ignores CRLF](<inline comment link>) | important | hard | VALID | 4ab12cd… |
| F2 | Stale version (`README.md:12`) — details below | nit | normal | PARTIAL | 9e01f2a… |
| F3 | [Retry loop unbounded](<link>) | important | normal | DEFERRED: needs a product decision | — |

**Checks:**

- helper samples ✅
- regression checks ✅
- commit verification ✅
```

- Write no narrative paragraph. Header bullets are `- Label: value`, in this order:
  - `Reviewed:` a compare link from merge base to reviewed head (the head repository's URL for a cross-repository PR), with short SHAs as its text, then `(full diff)`, `(range <from>...<to>)` or `(full diff: <fallback reason>)`.
  - `Reviewer:` model/effort and any focus for each reviewer, comma-separated. In inline mode, when Factory built or fixed the reviewed code, add `(not independent of the build)`.
  - `Guidance:` the guidance file names.
  - `Fixes:` `published through <full SHA>`, `kept local: <reason>`, or `none (no findings)`.
- Write SHAs as plain text, never in backticks or code blocks, so GitHub links them; use the full SHA, which GitHub shortens. In a fork PR, write `OWNER/REPO@<sha>` for head-repository commits.
- Write finding IDs on GitHub as `F1`, `F2`, never `#1`, which GitHub links to issue or PR 1; this includes inline comments, replies and Diagnostics work cells. Give one row per finding in ID order. Finding is a short title linked to its inline comment or thread when there is one. Severity is the rating (`important` or `nit`). Difficulty is `hard` or `normal` after merging reviewers. Verdict is the `fix-issues` verdict (`VALID`, `PARTIAL`, `ALREADY_FIXED`, `INVALID`, `NOT_WORTH_FIXING`, `FAILED`, `DEFERRED`, `FOLLOW_UP` for pre-existing findings), with `: <reason>` when there is no commit. Commit is the fix SHA or `—`. A clean round has no table.
- Put location, issue, impact and outcome in the body only for findings the `review` helper moved there because they had no anchor; anchored findings keep those details in their inline comment.
- End with a `**Checks:**` label followed by a bullet list, one check and its result per bullet and a final `Not run:` bullet for skipped checks when any, then an `**Open questions:**` list when there are any. The Diagnostics block follows.

### Fix recovery

In every execution mode, before starting a nonempty fix attempt, save the original reviewed comparison and review results (including findings with their IDs), checkout path and branch, and the verified local tip (initially the reviewed head). Save each set's triage order before starting it. Keep the completed prefix of verdicts with reasons, checks, CHANGES files and full commit SHAs or `null`, and the pending finding ID, if any. Write these together atomically with `scripts/factory.mjs checkpoint set --file RECOVERY state VALUE_JSON`. The agent applying the batch writes during the batch. The round's owner writes for hard findings and between invocations. Only one agent may write at a time, and the recovery file is separate from the run checkpoint.

Before each finding, verify a clean tree at the recorded tip and save its pending ID. For a fix that will be committed, complete the Step 5 scope check in `fix-issues` and stage only the intended edits. Save the pending verdict, checks, files and staged tree SHA (`git write-tree`), then commit only after that write succeeds. After committing, confirm a clean tree and verify the commit's parent, tree and files against the saved data. In one update, append the verdict with its full SHA, advance the tip and clear the pending entry. For a verdict without a commit, confirm the tree is clean and record the verdict with the same tip in that update. Record deferred and follow-up items in order as verdicts without commits.

When resuming an interrupted fix attempt, including after a worker stops without returning results or a late `NO_NESTING`, confirm the previous writer and its workers have stopped. Before repeating review or starting another fixer, validate the saved comparison with Fix preflight and confirm the same checkout and branch and clean status. Require the completed verdicts to form a prefix of the saved order and any pending finding ID to be next. Require the recorded tip to descend from the reviewed head or equal it, match the ordered finding and corrective commit SHAs against `git rev-list --reverse REVIEWED_HEAD..TIP`, and run `verify-commits` over that range with the completed rows, accounting for recorded scope mismatches as described below. If `HEAD` equals the recorded tip, continue the pending work or the first unprocessed finding. If there is a pending staged tree and `HEAD` has exactly one parent (the recorded tip) and that exact tree, verify its files against the pending record, then record it as completed before continuing. For a pending correction, also recheck its expected net diff before recording it. A dirty tree, missing or inconsistent evidence, or any other unexplained tip stops recovery. Preserve the work and report the discrepancy without resetting, recommitting or pushing. Resume only unfinished findings in the saved order, batch before hard, and build the final verdict table from the finding records.

### Corrective commits

After the findings, correct scoped mismatches with a new commit. Before altering the checkout, save the exact offending SHAs and paths, the current clean tip, and the expected net diff for the affected paths against the reviewed head, retaining edits from in-scope fixes. Stop if that result cannot be established. Stage only the corrective edits and verify the staged net diff matches the expected result. Before committing, save the affected files and staged tree SHA in the pending correction using the same atomic update as for a finding. After confirming its parent, tree, files and net diff, add the correction's full SHA to the completed corrections, advance the verified tip and clear the pending correction in one update.

Append a separate row such as `{id: "correction-1", verdict: "CORRECTION", commit, files}` to the verification input for each completed correction. Keep the finding verdicts and their reported CHANGES files intact. Require `verify-commits` to report no missing or unreported commits and only out-of-scope entries that match the saved offending SHAs and paths. Check the recorded net diff for each completed correction on resume and again before the push. A pending correction may account for a recorded scope mismatch during recovery, but every mismatch must have a verified completed correction before pushing. Keep correction evidence with the round checks and out of the findings table.

### Round delivery

Before preparing any round delivery, take a fresh PR snapshot and use `compare same` against the original reviewed comparison. Apply Fix preflight's one-retry rule if it changed. After verifying the round's commits and before pushing anything, atomically save a `delivery` entry in the recovery file with `scripts/factory.mjs checkpoint set --file RECOVERY delivery VALUE_JSON`. Include the original reviewed comparison, PR identity and exact head repository and branch, verified tip, planned disposition (push, local-only or no fixes), and the round review and reply inputs. Keep the published round number, review scope and guidance, reviewed diff path or SHAs, reviewer results, verdicts, checks and any correction evidence, open questions, follow-ups, and source links and thread IDs. For a push, use `compare snapshot` with the exact tip to push and the PR snapshot's base ref and SHA to record the expected published comparison. For local-only or no fixes, use the original comparison as the expected published comparison.

When resuming with that entry, confirm the prior writer has stopped and that the PR is open with the recorded identity and head destination. Compare fresh PR state with both saved comparisons using `compare same`:

- For a planned push, if the comparison exactly matches the expected published comparison, record the push as verified and continue preparing the review from the saved inputs. This also applies if the original push returned an error or no result.
- If it matches the original reviewed comparison and there is no recorded verified push, resume the still-pending push only after rechecking authorization, the clean checkout and the saved tip against the round's commit verification. If the disposition was local-only or no fixes, continue without pushing. Report local-only fixes as local.
- Otherwise apply Fix preflight's one-retry rule for outside changes, keeping the previous record and local work. A previously verified push whose comparison has moved is outside change, even if the head returned to the original SHA.

When pushing, use the exact recorded tip and authorized destination, then verify the result against the expected published comparison and save the verified outcome back to `delivery`. Prepare the review and replies using the original reviewed comparison for anchors and the verified push outcome for commit citations. Persist their paths in `delivery` before the owner returns so the orchestrator can recover them. Record a verified round 1 push even when recovered, since it determines whether round 2 runs.

## 6. Post the final handoff

Open Final handoff before launching the handoff owner or starting its procedure in flat or inline mode.

**Prepare.** Snapshot the final PR comparison and use `compare same` against the expected published head and base fields. On unexpected changes apply step 1's refresh rule on the existing PR path, returning any approval to the orchestrator. On build paths, stop handoff for a changed comparison that the round procedure did not review. Run the facts stage of `summarize-changes`. For a diagnosed bug or existing PR review, use `diagnose-issue` with the approved report, baseline, reproduction and final head. Reuse evidence only for the same commits and reproduction. For a pinned spec, fetch its store to a fresh scratch file with the shell now (or with the light fetch worker without `gh`) and run `node PREPARE_SPEC_DIR/scripts/spec-record.mjs pin FILE --out DIR` into a fresh directory, without printing the body. Compare its revision and `spec_sha256` to the checkpoint. If `pin` escalates, run `check` on the same file and compare its revision and computed hash instead. If the approved revision moved, state the built revision and the current revision in the handoff and notification and give `$factory <spec>` to adjust. Name an unapproved edit, missing record or unreadable store when the revision cannot be established. Keep the pinned result.

Prepare the PR description's refreshed `## Summary` from the facts: two to five bullets of what changed with key files, then a **Try it:** line and a **Checks:** bullet list (one check and its result per bullet, plus a `Not run:` bullet when any were skipped), so it matches the final code. For Adjust, also prepare the new `spec-built` block with the pinned revision and hash, filled from `record.json` by the shell, and for a local spec the collapsed `<details><summary>Spec</summary>` document from `document.md`. For a legacy PR, the replacement removes its `## Spec rev N` section and uses the layout in `implement-spec`. Use `scripts/factory.mjs section --body FILE --heading TEXT [--match-prefix] --content FILE --out FILE` for the `## Summary` section. A legacy spec section is a verbatim document that can contain headings equal to or higher than the containing heading; in that case run the helper on a scratch file with only the old section's heading, and use the output to replace the span from that heading through the exact old spec body saved in the checkpoint. Supply the replacements and evidence identifying each old span to the orchestrator. The orchestrator re-reads the current description, confirms each old span matches uniquely, then applies only those replacements and verifies them with `spec-record.mjs built`, preserving `Closes #N`, unrelated content and the Diagnostics block. If the description already matches on resume, verify it and continue.

Also prepare the `## Reviewer notes` section for the end of the PR description, after `Closes #N` and the `spec-built` block and before the Diagnostics block, with these bullets in order, keeping any `**Diagnosis:**` bullet from step 2 first:

- **Where to look first:** review order and key files from the facts, with links to the PR's files.
- **Deferred:** remaining work, including failures and why they remain open.
- **Follow-ups:** pre-existing findings with their location, evidence and Review Round.
- **Open questions:** read `rounds.N.open_questions` for each completed round and include unresolved decisions or verification still needed from a human reviewer, with the originating Review Round.

Write `None` after an empty label. Insert or replace it with `scripts/factory.mjs section --body FILE --heading "## Reviewer notes" --content FILE --out FILE`, which places a new section before the Diagnostics block, and give the orchestrator the replacement with the other description edits.

Prepare the `Final handoff` comment with the final comparison, facts, checks, source report and verification evidence where applicable. Do not repeat the findings, which the round reviews already list. Instead, give one line per Review Round with its review link and counts (for example, `- Review Round 1: 3 findings — 2 fixed, 1 deferred`, or `clean`), then a link to the PR description's Reviewer notes. The orchestrator rechecks the comparison with `compare same` before publishing, applies the description edits, closes the window, and adds its Diagnostics block. Post and verify the comment and its URL, then rewrite the PR description Diagnostics with the same stages to refresh `Run so far`, and verify the description.

## 7. Mark the PR ready and notify

Open Ready after verifying the handoff and the PR description. Confirm with `compare same` that the open PR still matches the comparison named in the handoff. If the comparison changed, report the mismatch and stop before changing the PR status. On diagnosis paths, require `VERIFIED` for that final comparison before marking a draft ready. If verification fails or is inconclusive, report the handoff link, current PR status, and blocker, then stop.

Unless the user asked to keep the PR in draft, mark it ready for review with authenticated `gh pr ready NUMBER` or the equivalent GitHub MCP operation. Skip the mutation if the PR is already ready. Verify the resulting status. If the transition fails, report the blocker and resume at this step when it is resolved. Close Ready after verifying the result. Keep the Ready tail in chat as described in Stage bookkeeping and publication.

Send the user the PR and final handoff links with the verified PR status and the run total from `pr-diagnostics` (tokens and cost, or why unavailable), using a push notification if the harness offers one and a chat update otherwise. Stop here and wait for interactive follow-up.

## 8. Stop and resume on a usage limit

Keep the checkpoint's scratch file path in harness task state. Record these keys as the run progresses:

- `entry_path`, `checkout`, `branch`, `pr` (URL, repository and refs), `pr_status`, `last_completed_step`, `execution_mode`, `execution_mode_reason`, `root_model`, and `model_check_asked`.
- `spec` (store, pinned directory and `record.json` path, revision, hash, `meta`, and any `pin_escalated` reason), `build` (estimate, model and effort including overrides, attempts, starting head, commits, checks and stopped payloads), and `description` (verified comparison and whether step 2 wrote its Diagnostics).
- `diagnosis` (source report, approval, reproduction, baseline, tested comparison or commits, and verification outcomes) and `adjust` (original built document path and source, pre-build comparison, and published stage numbers).
- `rounds.1` and `rounds.2` (reviewed comparison under `reviewed`, selected range or reason for full diff, reviewers and foci, guidance, findings, `open_questions`, `fix_recovery` path, fix outcomes and SHAs, pushed head, payload paths, posted review and reply links, and follow-ups). For example, read the first reviewed head with `checkpoint get --file F rounds.1.reviewed.head`.
- `handoff` (comparison, body paths, verification results and comment link), `stages.NAME` (windows, usage reports, Diagnostics and outcome), `run` (harness and session source), and any unsent stop notice under `resume_notice`.

Resume the existing run from this checkpoint, including its mode and approvals, even if the PR description was updated. Reuse an existing open stage rather than opening it again. Reuse a closed stage's Diagnostics if only publication is pending.

On a usage limit, stop starting new work. If the PR exists and the harness still permits a GitHub write, post a PR comment with the step and round where work stopped, the relevant comparison or findings, and the next step to resume. If the limit prevents posting or precedes PR creation, keep the notice in the checkpoint and surface it to the user when possible. On resume, post the notice once a PR and write access are available. Check current GitHub state and the checkpoint before retrying a push, review, comment, or ready-for-review transition. Before republishing a round, look for a review and replies for the same round and reviewed comparison. Record existing links and publish only missing results. Resume from the first incomplete step using the existing PR and approval.

When resuming in a new session, split an interrupted stage at the resume time. With the original source still in `run`, use `scripts/factory.mjs stage close --file F --stage NAME --until RESUME_TIME --session-id ORIGINAL_ID [--transcript PATH]...` to save that part and keep the stage pending. Pass the original transcripts explicitly when using a host export. If only an export can identify the session, pass its `--transcript` paths as the override. Set `run` to the new session source and close normally when the stage finishes. The helper resumes from the last part and sums all parts. Keep incomplete stages and totals marked incomplete. Check the ledger against the checkpoint and fix missing rows.
